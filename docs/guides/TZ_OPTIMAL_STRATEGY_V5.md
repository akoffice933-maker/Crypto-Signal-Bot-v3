# ТЗ: внедрение `OPTIMAL STRATEGY.docx` в текущий код бота

## 1. Цель

Подготовить и внедрить в текущий проект `Crypto Signal Bot` рабочую версию стратегии из файла `OPTIMAL STRATEGY.docx` так, чтобы:

- бот корректно работал в текущем рыночном режиме BTCUSDT с низкой волатильностью;
- логика документа была приведена к текущей архитектуре проекта, а не внедрялась "как есть";
- новые правила не ломали текущий pipeline, Telegram-нотификации, БД и веб-маршруты;
- стратегию можно было включать поэтапно и проверять на каждом этапе.


## 2. Основание

Источник требований: `OPTIMAL STRATEGY.docx`.

Документ описывает стратегию `v5 Precision — Dual Mode`, в которой:

- вводится режим `NORMAL` и `QUIET` в зависимости от `ATR%`;
- `QUIET`-режим адаптирован под рынок с `ATR 0.20%-0.69%`;
- `Breakout` отключается в `QUIET`;
- вводятся отдельные пороги по confidence, volume spike, RR, risk;
- добавляются `Level Score`, паузы после серии убытков и дополнительные risk controls.


## 3. Текущее состояние проекта

На момент написания ТЗ код реализует:

- один общий pipeline без dual-mode;
- две стратегии: `sweep_reversal` и `breakout`;
- единые глобальные пороги из `config/settings.py`;
- один фильтр `tradeable`, который зависит от `ADX`, `ATR%` и сессии;
- cooldown сигналов через `signal_cooldowns`;
- `LiquidityLevel.strength`, но без полноценного `Level Score 0-9`;
- нет отдельного risk-state по сериям убытков;
- нет `Choppiness Index`;
- нет `Liquidation Reversal` как отдельной третьей стратегии.

Важно:

- документ `OPTIMAL STRATEGY.docx` не соответствует текущему коду один к одному;
- в документе есть элементы будущей версии, которых в проекте нет;
- поэтому внедрение должно быть staged, а не "переписать всё сразу".


## 4. Область работ

В рамках ТЗ нужно реализовать:

1. Dual-mode логику по `ATR%`.
2. Раздельные пороги для `NORMAL` и `QUIET`.
3. Ограничение стратегий по режиму.
4. Level Score для уровней ликвидности.
5. Risk controls по серии лоссов.
6. Новые логи и диагностические признаки.
7. Тесты на mode selection, filters, score и risk-pauses.

Вне рамок первого этапа:

- полная переработка Telegram-форматтера;
- новая стратегия `Liquidation Reversal` в отдельном async-потоке;
- изменение веб-интерфейса кроме необходимых диагностических полей;
- рефакторинг всей системы риск-менеджмента под реальное исполнение ордеров.


## 5. Целевое поведение

### 5.1 Выбор режима

Бот должен автоматически выбирать режим по `ATR%`:

- `NORMAL`, если `ATR% >= 0.70%`
- `QUIET`, если `0.20% <= ATR% < 0.70%`
- `BLOCKED`, если `ATR% < 0.20%`

### 5.2 Поведение по режимам

`NORMAL`:

- разрешены `sweep_reversal` и `breakout`;
- Asian/London/NY разрешены;
- применяются normal thresholds;
- используется более агрессивный risk profile.

`QUIET`:

- разрешён только `sweep_reversal`;
- Asian session запрещена;
- используются quiet thresholds;
- риск ниже;
- цели ближе;
- RR допускается ниже, чем в `NORMAL`, но не ниже допустимого quiet-минимума.

`BLOCKED`:

- pipeline завершает цикл без сигнала;
- в логах указывается причина `ATR below quiet minimum`.


## 6. Этапность внедрения

### Этап 1. Стабилизация текущего pipeline

Цель:

- устранить runtime-ошибки, мешающие дойти до стратегий;
- выровнять диагностические логи с фактическими настройками.

Обязательно:

- исправить совместимость `engine.logger.log_liquidity_levels()` с `LiquidityLevel`;
- убрать хардкод старых порогов из pipeline-логов;
- убедиться, что при `Tradeable=True` цикл доходит до `sweep/breakout/no signal`.

Критерий готовности:

- нет падения pipeline после `Tradeable=True`;
- тесты по liquidity/logger проходят.

### Этап 2. Введение ATR-based mode selection

Цель:

- убрать единый жёсткий low-volatility skip;
- разрешить quiet-рынок обрабатывать по отдельным правилам.

Нужно:

- добавить в `MarketContext` поле `operating_mode`;
- изменить `tradeable`-логику так, чтобы `QUIET` не блокировался полностью;
- логировать выбранный режим на каждом цикле.

Критерий готовности:

- для ATR в quiet-диапазоне бот не делает ранний `SKIP`, а идёт дальше в pipeline;
- `BLOCKED` срабатывает только ниже нижнего quiet-порога.

### Этап 3. Раздельные пороги `NORMAL` / `QUIET`

Цель:

- перенести mode-specific параметры в конфиг;
- исключить захардкоженные различия внутри стратегий.

Нужно:

- добавить набор параметров `normal_*` и `quiet_*` в `config/settings.py`;
- сделать helper доступа к profile-параметрам по текущему режиму;
- использовать их в `sweep_reversal`, `breakout`, `confidence`, `pipeline`.

Критерий готовности:

- все mode-specific пороги читаются централизованно;
- стратегии не используют старые глобальные значения там, где должны быть mode-specific.

### Этап 4. Ограничение стратегий по режиму

Цель:

- реализовать фактическое различие поведения режимов.

Нужно:

- `breakout` запускать только в `NORMAL`;
- `sweep_reversal` разрешить в обоих режимах;
- в `QUIET` отключать Asian session;
- в логах явно писать, почему стратегия не запускалась.

Критерий готовности:

- в `QUIET` не может появиться `Breakout signal`;
- в `QUIET` сигнал не может быть отправлен из Asian session.

### Этап 5. Level Score для Liquidity Map

Цель:

- уменьшить шум по слабым уровням;
- приблизить логику к `OPTIMAL STRATEGY.docx`.

Нужно:

- добавить score `0-9` для `LiquidityLevel`;
- score должен учитывать:
  - свежесть уровня;
  - число касаний;
  - таймфрейм;
- отбрасывать уровни ниже порога:
  - `NORMAL >= 5`
  - `QUIET >= 7`

Допущение:

- если часть признаков из docx недоступна в текущих данных, score должен быть реализован по доступным полям с явной документацией формулы.

Критерий готовности:

- уровни ниже порога не попадают в стратегию;
- score виден в логах и при необходимости в API/экспорте.

### Этап 6. Risk controls по серии лоссов

Цель:

- снизить риск при деградации рынка;
- добавить safety-механику без реального исполнения ордеров.

Нужно:

- хранить streak убыточных сигналов/закрытых сделок;
- снижать `position_size_pct` после заданного количества убытков подряд;
- вводить временную паузу после заданного количества убытков подряд;
- pause должна проверяться в pipeline до отправки сигнала.

Критерий готовности:

- при достижении порога pause сигнал не отправляется;
- причина отражается в логах.

### Этап 7. Расширенная диагностика и тесты

Цель:

- сделать новую логику проверяемой.

Нужно:

- добавить тесты выбора режима;
- добавить тесты запрета Asian в quiet;
- добавить тесты на Level Score threshold;
- добавить тесты risk pause / reduced risk;
- добавить интеграционный тест, где:
  - цикл проходит `Tradeable=True`;
  - выбирается режим;
  - стратегия запускается или блокируется по mode-rules;
  - pipeline не падает.

## 8. Нефункциональные требования

- Все изменения должны быть покрыты тестами.
- Pipeline не должен падать из-за логирования или диагностических helper-функций.
- Новая логика должна быть feature-flag friendly: по возможности режимы должны включаться конфигом.
- Все числовые пороги должны быть вынесены в `settings.py`.
- Логи не должны содержать устаревших или захардкоженных значений, если они уже настраиваются через `settings`.


## 9. Критерии приёмки

Функциональные:

- бот различает `NORMAL`, `QUIET`, `BLOCKED`;
- при quiet-рынке pipeline не завершает цикл раньше времени;
- в quiet-режиме работает только `sweep_reversal`;
- Asian session запрещает quiet-сигнал;
- уровни ликвидности ниже threshold не участвуют в стратегии;
- risk-pause блокирует отправку сигнала при достижении порога;
- pipeline доходит до `No signal this cycle` или `SIGNAL FOUND`, не падая на внутренних helper-логах.

Диагностические:

- в логах есть `mode`, `tradeable`, `strategy allowed/blocked`, `risk pause status`;
- blocker-тексты соответствуют реальным значениям конфигурации.

Тестовые:

- есть unit-тесты по mode selection;
- есть unit-тесты по Level Score;
- есть тесты по strategy gating;
- есть интеграционный тест полного цикла без runtime error.


## 10. Порядок реализации

Рекомендуемый порядок:

1. Стабилизация текущего runtime.
2. Mode selection по ATR.
3. Strategy gating по mode.
4. Mode-specific thresholds.
5. Level Score.
6. Risk pause / reduced risk.
7. Дополнительные улучшения из docx.

Такой порядок нужен, потому что он сначала устраняет блокеры сигнала, затем увеличивает покрытие рынка, затем повышает качество.


## 11. Что не внедрять в первой итерации

Не включать сразу:

- `Liquidation Reversal` как третью стратегию;
- новый отдельный async-поток, не встроенный в текущий цикл;
- сильный рефакторинг всей архитектуры проекта;
- переписывание БД под execution engine;
- любые изменения, которые невозможно покрыть тестами быстро.

Причина:

- это сильно увеличит объём и риск регрессий;
- сначала нужно получить устойчивый dual-mode pipeline на существующей архитектуре.


## 12. Ожидаемый результат после внедрения первой рабочей версии

После внедрения этапов 1-4 ожидается:

- бот начнёт обрабатывать текущий quiet-рынок, а не молчать из-за общего ATR-фильтра;
- количество циклов, доходящих до стратегий, вырастет;
- диагностика станет прозрачной;
- можно будет объективно понять, что режет сигналы:
  - mode,
  - level score,
  - confidence,
  - session,
  - risk pause,
  - отсутствие паттерна.

После внедрения этапов 5-6 ожидается:

- уменьшение шума по слабым уровням;
- более стабильное поведение при серии плохих сделок;
- closer match к логике `OPTIMAL STRATEGY.docx`.
